> 位置付け：開発に使用する初期仕様。介入の効果と状態分類の妥当性は未検証。閾値は予備実験でのみ調整し、本実験前に固定する。

## 0. 研究目的と検証範囲

対象はC言語の基礎文法を履修済みでポインタが未履修の大学生、1人120分程度。生成AI利用中の援助要請（HS）と回答利用（RU）を各Passive/Active/Constructiveに分類し、状態に応じて5種類の認知的関与支援または非介入を選択する。比較相手は状態に依存しない固定の動作予測・検証支援。RQ1は推定精度、RQ2は支援停止後の自発的な問題解決行動、RQ3は支援負担。比較で示せるのは「システム全体の差」であり、支援種類・頻度・タイミングの独立効果ではない。

## 1. 推定方式（本番系は一つ）

**ハイブリッド特徴抽出＋決定規則による分類**。プロンプト・追加質問の意味特徴だけLLMで抽出し、コード差分・構文木・貼り付け・実行系列はプログラムで計算する。最終状態は固定したルールで決定する。ログ全文をLLMに渡して直接9分類する方式は本番の介入には使わず、事後研究用の比較モデルとして分離する。特徴値・元イベントID・規則バージョン・判定時刻・Unknown理由を必ず保存する。

対象言語は**C**。Tree-sitter Cで具体構文木（CST）を解析する。Python標準のast/tokenizeをCソースに使用しない。コード実行は時間・メモリ・ネットワーク・ファイルアクセスを制限した隔離サンドボックスで行う。

【v1.1】LLMの出力（特徴抽出・支援問題生成・記述採点）は、プロンプト・モデル名・パラメータ・生出力とともに保存する。ログ再生（§10）は保存済みのLLM出力を用い、LLMを再呼び出ししない。

## 2. ログ収集と分析区間

【v1.1】学習環境を新規開発するため、以下を常時取得する。

| イベント | 内容 |
|---|---|
| PROMPT_DRAFT_SUBMIT | 学習者が送信ボタンを押した時点の原文（P-A介入の有無に関わらず記録） |
| PROMPT_SENT | 実際にAIへ送った文面。P-A介入後に変更された場合は原文との差分も記録 |
| AI_RESPONSE | 回答全文、抽出したコードブロック（block_id付き） |
| CODE_EDIT | エディタの全変更操作（位置・削除文字列・挿入文字列・入力種別：打鍵/貼り付け/取り消し等） |
| COPY_FROM_AI | AI回答ペインからのコピー（response_id、block_id、選択範囲） |
| PASTE | 貼り付け。直前のCOPY_FROM_AIと文字列が一致すれば source=ai と由来（response_id/block_id）を付与。それ以外は source=external/unknown |
| CODE_SNAPSHOT | 固定間隔（例：10秒）および編集・実行時のエディタ全文。CODE_EDITの欠損に備えた冗長記録 |
| COMPILE / RUN | 入力・出力・終了コード・エラー・コンパイラ警告 |
| SUPPORT_SHOWN / SUPPORT_ANSWER / SUPPORT_HINT / SUPPORT_END | 支援の提示・回答・ヒント・終了理由（完了/スキップ/中断/時間切れ） |
| SUPPORT_RUN | 【v1.1】支援UI内で行われた実行。RU特徴量・自発行動の評価から除外する |
| TASK_END | 課題終了 |

各ログに匿名参加者ID、群、課題ID、時刻（サーバ時刻）、cycle_id、規則バージョンを記録する。ログは追記のみ（上書き・削除しない）とする。欠損値は0として扱わない。

【v1.1】**支援中フラグ**：SUPPORT_SHOWN から SUPPORT_END までの間に生じたイベントは in_support=true を持ち、RU特徴量（T/E/I/D/S/C）の計算対象から除外する。支援UIはエディタを操作不能にするため、通常この間に CODE_EDIT は発生しない。

1サイクル＝一つの新規質問→AI回答→関連する編集・実行・確認質問→終了。次の独立した質問または課題終了で確定する。90秒の無操作は暫定的な区間クローズの候補とし、無操作だけをPassive判定の根拠にしない。関連する確認質問は可能な限り同じサイクルにまとめ、その対応付けの曖昧な場合はreview_requiredを立てる。HSは質問時点で分類、RUは回答後の観察から更新し、十分な証拠がなければUnknown。未来ログを使用しない。

【v1.1・暫定】新規質問／確認質問の判定は §13-1 で確定する。確定までの既定動作は §13-1 の案Aとする。

## 3. HS：特徴と決定規則

LLMに以下の0/1特徴と根拠となる原文スパンをJSONで出力させる：h1 完成コード要求、h2 問題・構文・エラーの具体的指示、h3 自分の仮説や考えの提示、h4 希望する支援形式の主体的指定。否定（「完成コードではなく」）を正しく取り扱う。パース失敗時はUnknownでありPassiveとはしない。

暫定規則： (h3=1 OR h4=1) → Constructive、それ以外でh2=1 → Active、それ以外 → Passive。h1は行動の記録・競合検出用とする。h1=1とh3/h4=1が併存するプロンプトは原文とともに競合フラグを記録し、人手レビュー候補とする。質問前の自力試行回数は別の補助特徴であり、HSラベルを自動昇格させない。仮説・自己診断の入力は強制しない。

【v1.1】HSは**PROMPT_DRAFT_SUBMIT の原文**（学習者が自発的に書いた文面）で判定する。P-A介入によって変更された文面（PROMPT_SENT）のHSも参考値として別に保存するが、状態判定には使わない。

## 4. RU：特徴量計算

AI回答からCコードの候補を抽出し、編集位置・関数名・課題識別子で学習者の対象コード範囲に対応付ける。対応付け不能・コードなし・十分な証拠なしの場合、関連特徴をUnknownにし、無理にPassiveとはしない。

【v1.1】RU特徴量は in_support=false のイベントのみから計算する（§2）。

- D：AIコードと対応する編集後コードのC言語トークン列を比較し、`(削除元トークン数 + 置換元トークン数 + 挿入トークン数)/(AI元トークン数+挿入トークン数)`を計算。編集履歴（CODE_EDIT・PASTEの由来）から、どのAI回答に由来するかも追跡する。単なる変数名変更による過大評価に注意。
- S：Tree-sitter Cの構文木から変数名・コメント・位置情報を除く正規化構造系列を生成。LCSの長さLから `1-2L/(len_before+len_after)` を求め、0.10以上かつif/for/while/call/pointer関連操作等の構造変更があれば1。構文エラーで比較不能ならUnknown。これは真のAST木編集距離ではなく正規化CST構造差分。
- C：PASTE(source=ai) から追跡できるAI由来トークン数÷対象コード総トークン数。【v1.1】AI回答を見ながら手で打ち直した場合はPASTEが発生しないため、Cは0ではなく、別特徴`text_similarity`（AIコードとの正規化トークン類似度）を併記する。`text_similarity`はCに代入しない。
- T：同じ対象処理についての実行・テスト回数。単なる実行ボタンの反復と異なる入力によるテストを区別。SUPPORT_RUNは数えない。
- E：①言語化された仮説→対応する変更→実行・確認、または②異なる入力2種類以上でテスト→結果を受けて修正→以前のテストの再実行、という観察可能な検証系列があるとき1。それ以外0、観察不十分ならUnknown。②は内的な仮説そのものを確認したわけではない。
- I：対象処理の新規作成、手入力由来トークン80%以上、AIコードとの正規化構造類似度0.70未満、実行1回以上のすべてを満たす場合1。手入力は理解の証明ではない。
- Q：回答の内容・正しさを問う確認質問があれば1。単なる「続けて」や別の完成解答要求は0。

暫定RU決定規則（上から順に評価）：
1. `E==1 AND (T>=2 OR I==1)` → Constructive。
2. それ以外で `D>=0.10 OR S==1 OR Q==1` → Active。ただし無関係な編集、コメントのみ、機械的な改名のみなら人手確認フラグを付す。
3. それ以外で `(C>=0.80 AND D<0.10)` または明確な無変更採用イベント → Passive。
4. それ以外 → Unknown。無操作・未質問・証拠欠損はPassive扱いしない。

HS×RUで9状態（P-P/P-A/P-C/A-P/A-A/A-C/C-P/C-A/C-C）を構成。Unknownが片方にあればPending。提示された支援を遂行した操作は自発行動の評価には含めない。

## 5. 介入機会と時間的整合性

質問nの**最新RUは、その回答を利用する前には分からない**。よって新しい質問nについての介入には、**先行する完了済み2サイクルのみ**を用いる。分析対象は本課題の自発的なAI利用サイクル。導入時の共通AI活動はログに保存するが介入の2サイクル数には含めない。

【v1.1】**判定窓**：判定窓は「直近に完了したサイクルのうち、支援を提示しなかった（intervened=falseの）サイクル2つ」とする。支援を提示したサイクルは、その後の操作が支援の影響を受けるため窓から除外する。クールダウンで非介入となったサイクルは窓に含める。窓の構成規則は両群で同一とする。（介入前のサイクルを介入後の窓で再利用するかは §13-2 で確定する。）

【v1.1】**介入判定の時点**：判定は質問nの**送信時（PROMPT_DRAFT_SUBMIT）**に一度だけ行う。窓は送信時点で確定しているため、送信前に判定してもRUの時間的整合性は保たれる。判定結果（介入するか、どの支援か、非介入理由）はこの時点で記録する。

【v1.1】**単一の介入機会**（支援の種類で提示の位置が分かれる）

- **送信前型（P-A：質問の具体化のみ）**：送信ボタン押下→判定→質問の具体化オーバーレイ→学習者が送信文面を確定→AIへ送信→AI回答を表示し、直ちに編集・実行可能。この機会で2つ目の支援は出さない。
- **回答後型（上記以外の4支援、および一律群）**：送信ボタン押下→判定→AIへ送信→AI回答を画面に読み取り専用で表示→支援オーバーレイを提示→終了後に通常のコード編集・実行を可能にする。
- **非介入**：送信→AI回答を表示し、直ちに編集・実行可能。

内容のない回答や実行予測課題が構成不能な場合は両群とも「実施不能」として記録し、その機会で支援しない（この機会はintervened=falseとし、クールダウンも開始しない）。質問に紐づくサイクルnのRUは、支援終了後の操作からのみ算出する。

【v1.1】読み取り専用表示中のAI回答ペインからのコピー可否は §13-4 で確定する。

直近2サイクルがUnknownを含む、または学習目標外の操作である場合は適応群の介入を保留する。支援を一度出した後の**次の適格な1機会は両群ともクールダウン**（非介入）とする。新しいサイクルが終われば判定窓はローリング更新。これは誤介入と連続介入を減らす初期設計であり、有効性は未検証。サイクルが2回に達しない参加者は自動介入されないことを研究上の制約・評価項目として記録する。

## 6. 9状態からの適応的支援ポリシー

現行HackMDの5支援マッピングを維持するが、RU=Passive以外は無条件介入しない。ここで「候補」は即時支援を意味せず、直近2つの**候補状態**が連続して初めて支援する。各サイクルの候補判定と、どの支援を出すかを区別する。

| HS＼RU | Passive | Active | Constructive |
|---|---|---|---|
| Passive | 候補：問題の分解 | 条件付き候補：質問の具体化【送信前】 | 非介入 |
| Active | 候補：自己説明 | 非介入 | 非介入 |
| Constructive | 候補：動作予測・検証 | 条件付き候補：自力応用 | 非介入 |

条件付き候補の追加条件：P-Aは、直近の質問が曖昧（h2=0）かつ前回の回答利用に明確な修正・検証を認める場合。C-Aは、現在課題の重要概念について自力適用が未観察で、AI利用後の編集はあるが検証的な転移が未観察の場合。この追加条件は完全な観察可能述語に実装し、曖昧なら候補としない。連続2サイクル候補なら、**最新完了サイクル**のセルの支援を選択する。2回が別セルでもよい。支援内容が現在の課題と無関係なら「実施不能」として記録する。

5種類の最小実装：
1. **問題の分解（P-P）**：現在の課題を2〜3手順に分ける選択/記述を1問出す。正解解法は即表示しない。
2. **質問の具体化（P-A）【v1.1：送信前】**：送信しようとした原文をそのまま表示し、直近のエラー（直近のCOMPILE/RUNのエラーから選択肢を作る）または不明点を選ばせ、今何を知りたいか一文で書かせる。システムは原文を書き換えない。学習者は「原文＋追記した一文」で送るか、「原文のまま」送るかを選ぶ。どちらを選んだかを記録する。
3. **自己説明（A-P）**：現在提示されたAIのコードの重要な1〜3行が果たす役割を説明させる。
4. **動作予測・検証（C-P）**：サンドボックスで確かめられる入力例に対して出力または変数の値を予測し、実行結果と比較する。
5. **自力応用（C-A）**：本問と同じ原理を用いる小さな条件変更を提示し、変更点を自分で実装させる。

支援UI：原則1問＋必要時ヒント1回＋再挑戦1回。正誤フィードバックの後に終了、追加的な強制は行わない。無回答・中断・スキップ（許可するかどうかは実験前固定）を全て保存する。AI回答は読めるが、回答利用に移る前に共通の支援インターフェースを通る。提示UI・最大所要時間・中断操作は両群で共通にする。

【v1.1】**支援問題の生成と検証**（両群共通）
1. LLMが、現在のAI回答コード・課題メタデータ（§14）・支援種別から問題案を生成する（JSON：問題文、選択肢または記述、正答、ヒント、根拠となる行番号）。
2. 実行を伴う問題（動作予測・検証、自力応用の確認用テスト、一律群のTrace-and-Predict）は、サンドボックスで以下をすべて満たした場合のみ提示する。
   - `-Wall -Wextra` でコンパイル成功、AddressSanitizer/UndefinedBehaviorSanitizer で実行時エラーなし
   - 同一入力で3回実行し出力が完全一致（非決定的な出力を排除）
   - 時間・メモリ制限内に終了
   - 正答にアドレス値（`%p`の出力等）を含まない。ポインタについては「指す先の値」のみを問う
   - 正答はLLMの予想ではなく、**実際の実行結果**を用いる
3. 生成または検証に失敗した場合は1回だけ再生成し、それでも失敗すれば「実施不能」（理由コード付き）として記録する。
4. 生成時間の上限を設け（例：15秒）、超えた場合も実施不能とする。学習者には「支援なし」と同じ画面を表示する。

記述式回答のフィードバック方式は §13-3 で確定する。

**注意**：P-A・C-Aに介入する教育的必然性は弱く、追加条件の妥当性は特に予備実験で検証する。検証で成立しない場合は本実験前に両セルを非介入へ変更することを事前に決めておく。
【v1.1】P-Aのみ送信前に介入するため、提示タイミングが他の支援・一律群と異なる。これは群間比較の解釈上の制約として報告する。

## 7. 一律支援群（比較条件）

両群共通の適格な機会（判定窓が2サイクル揃っている、対象AI応答と実行予測課題を構成可能、非クールダウン）では、**学習状態に関係なく毎回同じTrace-and-Predict型の支援**を表示する（回答後型）。

内容：現在のCプログラム（AI回答のコードまたはその短い重要箇所）と、§6の手順で検証済みの安全な入力例を表示し、出力またはポインタが指す値を1問予測→選択・記述→実際の実行結果と対比→誤答ならヒント1回・再挑戦1回→終了。表示タイミング、UI、最大所要時間、支援後の操作許可は適応群と同一。学習者のHS/RU推定は両群でバックグラウンド実施するが一律群の選択には使用しない。

比較の解釈：「一律に同じ支援を出すポリシー」と「状態に応じて5支援／介入なしを選ぶポリシー」という**全体比較**。両群で提示回数・支援種類が異なるため、9状態利用自体の独立効果や各支援の優劣を因果的には主張しない。共通機会数、実介入率、支援種、支援への応答、負担を報告する。

## 8. 9状態が必要な理由と検証

RUは「支援が必要そうか」を示す主な情報、HSは「どの支援が適切そうか」を区別する追加情報。例えばRU=Passiveでも、P-Pは問題の分解、A-Pは説明、C-Pは動作予測とし、同じRUでも支援内容を変える仮説を検証する。P-C/A-C/C-Cは回答利用が構成的であれば原則非介入。9状態がRUのみ3状態より必ず優れているとは主張しない。

分析案：RQ1はHS・RUを別々に評価。RQ2は適応群と一律群の後続課題における自発的行動（支援指示による行動は除外）を比較。探索的には「RUのみで決める仮想ポリシー」と「HS+RUの9状態ポリシー」の介入選択の差、HSによる支援内容の分岐頻度を記述する。9状態の付加価値を因果的に実証するには別の比較群が必要なので、本研究では探索的評価にとどめる。

## 9. 評価と実験プロトコル

参加者：C基礎履修済み・ポインタ未履修。全員に同一教材・課題・AIモデル・時間・測定系。導入共通活動→短い事前テスト→主課題（支援あり）→**支援停止後の後続課題**（AIは引き続き利用可）→事後テスト・負担質問紙。時間配分は予備実験後に120分へ調整し本実験前に固定する。群割付は可能なら無作為に実施する。

- RQ1：支援提示前の情報だけに基づき、独立評価者2名以上でラベル付け。HS/RU Macro-F1、9状態一致率、混同行列、Unknown率、判定遅延を報告。分類に使用できたイベントのみラベル根拠にする。
- RQ2：後続課題での自発的なコード検証、修正理由に整合する編集、方略調整の行動割合を評価。支援に強制された行為と、支援後の自発行動を分ける。副次的にポインタ理解・転移テストを実施。
- RQ3：共通機会数、介入回数、中断時間、完了率、主観的認知負荷、必要性評価。不要介入は事後の学習者評価または独立評価者による基準を明確にし、単なる非介入の多さを「不要介入削減」とはしない。

【v1.1】予備実験で優先的に確認する指標：参加者ごとの新規質問回数の分布、Unknown率（HS/RU別、理由コード別）、実介入率（両群）、支援問題の実施不能率（理由コード別）、支援生成の所要時間。

主たる分析単位は参加者であり、同一参加者の複数サイクルを独立した人数として扱わない。分類基準・閾値・介入規則は予備実験で調整した後に凍結する。

## 10. 開発AIへの受け入れ条件（実装テスト）

- HS=Active、RU=Passiveの完了サイクルが2回続いたとき、3回目の質問に対するAI回答の閲覧・利用段階で自己説明支援が選択されること。
- 1回しか完了サイクルがない場合は介入しないこと。
- RUがUnknownのサイクルをPassiveとして誤処理しないこと。
- C言語の未完成コード、ポインタ演算、構文エラーに遭遇しても解析失敗で学習画面が止まらないこと。
- AI応答にコードがなく検証課題を構成できないときは、両群で実施不能理由を記録すること。
- 各判定の根拠イベント、抽出特徴、使用規則、状態、介入理由、支援応答がCSV/JSONで出力できること。
- 同一条件の入力ログを再生すると、同じ規則バージョンから同じ状態・介入判断が再現できること。【v1.1】再生は保存済みのLLM出力を使い、LLMを呼び出さないこと。
- C言語コードは隔離サンドボックスで実行し、CPU/時間/メモリ/ネットワーク/ファイルの制限を設け、APIキーはサーバーに置くこと。
- 【v1.1】適応群で直近2窓サイクルがP-A候補のとき、3回目の質問は**AIへ送信される前に**質問の具体化支援が提示され、HSは原文で判定されること。
- 【v1.1】支援UI内の実行（SUPPORT_RUN）がT・Eの計算に含まれないこと。
- 【v1.1】支援を提示したサイクルが以後の判定窓に含まれないこと。
- 【v1.1】支援問題の正答がサンドボックスの実行結果から設定され、検証に失敗した問題が提示されないこと。
- 【v1.1】AI回答ペインからコピーして貼り付けたコードがPASTE(source=ai)として由来付きで記録されること。

## 13. 未確定事項（実装は既定値で進め、設定で切り替え可能にする）

1. **新規質問／確認質問の判定**
   - 案A（既定）：LLMで `is_followup`（直前のAI回答への言及・同一エラーへの追質問か）と根拠スパンを抽出し、確信度が低い場合は確認質問として扱い review_required を立てる。新規質問の取りこぼしは「介入機会の減少」側に倒れる。
   - 案B：チャットUIに「この回答について質問」（スレッド返信）と「新しい質問」を分け、学習者の操作で決める。決定的に判定できるが、学習者に分類を求めることが行動に影響しうる。
2. **介入前サイクルの再利用**：サイクルn-2, n-1で介入した後、n+2の判定窓が (n-1, n+1) になり、すでに介入の根拠に使ったn-1を再び使うことになる。
   - 案A（既定）：再利用を許す（合意どおり、介入サイクルだけを除外）。
   - 案B：最後の介入より後に完了したサイクルだけを窓に使う。根拠の二重使用は防げるが、介入間隔が実質的に長くなり、介入回数が減る。
3. **記述式回答のフィードバック**（問題の分解・自己説明・質問の具体化）
   - 案A（既定）：生成時にLLMが観点（ルーブリック）を作り、回答後にLLMが観点ごとの充足を判定して「満たした観点／不足している観点」を返す。判定と根拠を保存し、予備実験で人手監査する。
   - 案B：正誤判定はせず、模範解答・観点を提示して学習者が自己評価する。
   - 可能な限り選択式で出題し、記述式の比率を下げる。
4. **読み取り専用表示中のコピー**：回答後型の支援が出る場合、支援終了までAI回答ペインからのコピーを禁止するか（既定：禁止。非介入時は即時許可）。
5. **スキップ可否**：支援オーバーレイのスキップを許すか（既定：許す。スキップは記録）。
6. **学習者用AI・特徴抽出用LLMのモデルと提供元**、**学習者用AIのシステムプロンプト**（両群で固定）。
7. **実行環境**：設置サーバ（OS、同時参加人数）、サンドボックス方式（Docker／nsjail等）、標準入力の扱い（実行前に入力欄で一括指定する方式を既定とする）。

## 14. 実装構成（開発用の初期案）

- **フロントエンド**：ブラウザ単一ページ。左にCエディタ（打鍵・貼り付け・コピーをフックしてイベント送信）、右にAIチャット、下に実行（標準入力欄・出力欄）。支援はモーダルのオーバーレイ。
- **バックエンド**：Python。イベント受信API、AIチャット中継（APIキーはサーバ保持）、コンパイル・実行API、支援生成API、管理API。
- **イベントストア**：追記専用。SQLite（予備実験）→ PostgreSQL（本実験・同時参加が多い場合）。
- **判定エンジン**：イベント列を入力として、サイクル分割→特徴抽出→HS/RU判定→判定窓→ポリシー→介入判断を出力する**副作用のない関数**として実装する。本番と再生（§10）は同じコードを通る。
- **規則・閾値の設定**：バージョン付きの設定ファイルで管理し、各判定に規則バージョンを記録する。本実験前に凍結（ハッシュを記録）。
- **課題メタデータ**：課題ごとに、課題文、重要概念リスト、対象関数名、参照解、自力応用用の変形の種。
- **サンドボックス**：コンテナまたはnsjailでネットワーク遮断、CPU時間・メモリ・プロセス数・出力サイズ制限、読み取り専用ファイルシステム。
- **管理画面**：参加者登録・群割付、セッション開始／課題切替／支援停止（後続課題への移行）、ログのCSV/JSON出力。
